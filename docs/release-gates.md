## Capacity requirement still open
Target workload remains approximately 1,000 authenticated users. One action per 20 seconds means about 50 actions/second before multiple calls per action and notice refreshes. Read-only success does not prove that mix.

The normal two-worker Local FPM run previously stopped at the target stage on latency. A separate loopback runtime (five observed PHP server processes) later completed one 1,000-request stage at 50 scheduled requests/s, p95 1,877.5 ms, with no errors and all actors served. A timing-instrumented diagnostic run then stopped after 558 target-stage requests, p95 4,744.9 ms, again with correct returned account scopes and no response errors. Both results remain evidence; neither proves reliable 1,000-user operation.

Strict 500 ms read/1 s write targets still fail. PHP bootstrap and queueing dominate the measured native handler work. A thousand generated sessions with at most 50 in-flight individual API requests is not full browser/user-journey capacity, a soak or proof of CPU savings. No CPU-saving percentage is established. See capacity-local-results.md for runtime differences, exact scope and private timing evidence.

Do not repeat unchanged heavy load without a new measurement question or implementation change. Further experiments need controlled queue/runtime conditions and eventually representative deployment resources, plus sustained role-specific workflows and provider/sandbox gates. Keep the admission guards and include generator waiting time.

## Local request-body guard, 21 October 2026
The Next proxy limits request bodies to 20 MiB whether or not Content-Length is provided, gives body reads their own 30-second deadline, cancels stalled/disconnected streams, and admits at most four body-bearing submissions per Node process through upstream response headers. Saturation returns 429 before contacting WordPress; no automatic mutation retry is introduced. This is memory/admission protection, not proof of 1,000-user write throughput, and is not a distributed limiter. Six focused tests cover byte fidelity, declared and streamed size limits, stalled/aborted reads and admission release. All 24 Node tests pass.

Production build/TypeScript passed. Managed preview restarted; local /login returned 200. A deliberately oversized request to the local service-editor proxy returned 413 with the size-limit message before upstream dispatch. No live site was contacted.

## Local read session recovery, 21 October 2026
Client reads now recognize only HTTP 403 with the native rest_cookie_invalid_nonce code for one retry. A pending session refresh is shared among rejected reads; the refreshed authenticated user ID must equal the ID registered for the original nonce. Unknown nonces, changed/logged-out accounts, network errors, ordinary permission errors and aborted callers are not retried. Mutations are unchanged and never replayed by this helper. WordPress core rest-api.php confirms the qualifying error occurs during cookie authentication before REST handler dispatch; the local batch adapter retains native authentication. Five focused tests pass, all 29 Node tests pass, and production build/TypeScript pass. A real time-expired browser session and production-domain cookie behavior remain untested. No throughput claim is implied.
